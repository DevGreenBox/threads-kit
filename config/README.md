# Настройка мониторинга: пошагово

Этот файл написан для **не технаря**. Ничего программировать не нужно.
Всё, что здесь есть, можно делать через разговор с Клодом: покажите ему
нужный шаг и скажите «сделай вот это».

Порядок такой:

1. Получить доступ к API (один раз, самое долгое — ждём Meta)
2. Положить токен в окружение
3. Заполнить конфиг
4. Проверить на сухом прогоне
5. Включить

---

## Шаг 1. Получить доступ к API

### 1.1. Что вам понадобится

- Аккаунт в Threads, от которого будет идти активность
- Аккаунт Facebook (нужен, чтобы войти в кабинет разработчика Meta)
- Примерно **1–3 недели ожидания** на проверку заявки. Это не наша
  медлительность — так работает App Review у Meta.

### 1.2. Создать приложение

1. Откройте <https://developers.facebook.com/apps> и войдите.
2. Нажмите **Create App**.
3. В вопросе «What do you want your app to do?» выберите вариант,
   связанный с **Threads API**.
4. Название приложения — любое рабочее, его увидите только вы
   (например «Мониторинг Threads»).

### 1.3. Подключить Threads API

В приложении найдите раздел **Threads API** → **Set up**.
Там же будет кнопка добавления вашего Threads-аккаунта как тестового.
Добавьте свой аккаунт: до одобрения заявки всё работает только на нём.

### 1.4. Запросить разрешения (скоупы)

Это самый важный пункт, и именно здесь чаще всего ошибаются.
**Скоуп — это разрешение на конкретное действие.** Нужны пять:

| Скоуп | Зачем именно он нужен | Что не работает без него |
|---|---|---|
| `threads_basic` | базовый, без него не работает вообще ничего | всё |
| `threads_keyword_search` | **поиск по чужим постам** — сердце мониторинга | поиск найдёт только ваши собственные посты, и вы этого даже не заметите: ошибки не будет, просто чужих постов не будет в ответе |
| `threads_content_publish` | публиковать свои посты и ответы | нельзя отправить ни один ответ |
| `threads_manage_replies` | читать ответы под своими постами | не увидите, что вам отвечают |
| `threads_manage_insights` | свои метрики (просмотры, ответы, репосты) | аналитик не сможет посчитать, что сработало |

Скоуп `threads_manage_mentions` нужен только если захотите ловить упоминания
вашего аккаунта. Для мониторинга он не обязателен: у упоминаний нет
обычного эндпоинта для опроса, они приходят только вебхуками, а для этого
нужен публичный адрес в интернете. На старте — пропустите.

### 1.5. Что писать в заявке на App Review

Meta требует объяснить, зачем вам каждый скоуп, и **записать видео**, где
показано, как приложение это использует. Отказывают обычно за расплывчатое
описание. Пишите конкретно и честно.

Рабочая формулировка для `threads_keyword_search` (переведите на английский
или попросите Клода — заявка заполняется по-английски):

> Приложение ищет публичные посты, где люди описывают проблемы с их
> интернет-магазинами, и помогает владельцу аккаунта отвечать на них
> содержательно и вручную-подтверждённым образом, с жёсткими лимитами
> частоты. Приложение не собирает и не хранит персональные данные авторов,
> не публикует одинаковые ответы и не выполняет массовых действий.

Для `threads_content_publish`:

> Приложение публикует посты и ответы от имени владельца аккаунта,
> не более нескольких десятков в сутки, с проверкой на неуникальность текста.

**Важно:** не обещайте в заявке того, чего код не делает, и наоборот.
Проверяющий человек смотрит видео и сверяет с описанием.

### 1.6. Получить токен

После настройки в разделе Threads API будет кнопка генерации токена
(**Generate access token**). Токен — длинная строка вида `THAA...`.

Что о нём надо знать:

- Это **пароль от вашего аккаунта в Threads** для программы. Кто его получил,
  тот может писать от вашего имени.
- Короткий токен живёт 1 час, долгий (long-lived) — **60 дней**, потом его
  надо обновить. Берите долгий.
- ⚠️ **Если API не используется 28 дней, доступ отзывается.** Автоматика
  простояла месяц — токен перестанет работать не из-за поломки.

### 1.7. Чего с токеном НЕ делать

- ❌ не вставлять в `config/monitor.json` и вообще ни в какой файл проекта
- ❌ не присылать в переписке, не вставлять в задачи и тикеты
- ❌ не коммитить в git
- ✅ только в переменную окружения — как в следующем шаге

Код специально написан так, что токен вычищается из любых сообщений и
логов (`scrubToken`), и его нет даже в выводе отладки. Но если токен
попал в git — вычищать поздно: его надо **отозвать и выпустить новый**.

## Шаг 2. Положить токен в окружение

Самый простой способ — файл, который не попадает в git.

В репозитории уже есть заготовка `.env.example`. Скопируйте её и заполните:

```bash
cp .env.example .env
```

Откройте `.env` и вставьте токен после знака равенства:

```
THREADS_ACCESS_TOKEN=сюда_вставить_токен
```

`.env` уже перечислен в `.gitignore` — то есть в репозиторий он не уедет.
Это проверено заранее, ничего делать не нужно.

Перед запуском:

```bash
export $(grep -v '^#' .env | xargs)
```

Проверить, что токен виден программе, не показывая его:

```bash
node -e 'console.log(process.env.THREADS_ACCESS_TOKEN ? "токен на месте" : "токена нет")'
```

## Шаг 3. Заполнить конфиг

```bash
cp config/monitor.example.json config/monitor.json
```

Дальше правьте `config/monitor.json`. В примере у каждого поля есть
поле-объяснение рядом (те, что начинаются с подчёркивания — это комментарии,
программа их не читает).

### Что заполнить обязательно

**`свойUsername`** — ваш ник в Threads без собаки. Без него монитор будет
тащить в очередь ваши же посты.

**`темы`** — о чём слушаем площадку. Начните с **двух-трёх тем**, не больше.

```json
{
  "имя": "потерянные заявки с форм",
  "запросы": ["не приходят заявки с сайта", "форма на сайте не работает"],
  "ключевые": ["заявк", "форм", "сайт"],
  "тип": "RECENT",
  "лимит": 25
}
```

- `запросы` — что ищем. **Каждая фраза = один запрос к API.**
- `ключевые` — слова, которые должны реально быть в тексте поста. Это защита
  от случайных совпадений. Пишите **корни без окончаний** (`заявк`, а не
  `заявки`): русский язык склоняет, а поиск по корню поймает все формы.
- `тип` — `RECENT` (новые) почти всегда лучше `TOP`: в свежей ветке ответ
  заметят, в старой нет.

**`таймзона`** в блоке `предохранители` — ваша реальная таймзона
(`Europe/Moscow`, `Europe/Belgrade`, `Asia/Tbilisi`). По ней считается, когда
ночь и писать нельзя.

**`стопСлова`** — темы, куда не лезем ни при каких условиях. В примере уже
есть базовый список (политика, конфликты, чужие уязвимости, казино, крипто).
**Расширяйте его каждый раз, когда в очередь попало что-то неуместное.**
Это самая полезная привычка во всей настройке.

### Что можно не трогать

Блок `предохранители` уже настроен разумно. Важно понимать главное:

> **Ослабить эти лимиты через конфиг НЕВОЗМОЖНО.**

Поставите `"ответовВСутки": 5000` — применится 80, и в журнал попадёт запись
о том, что настройку зажали. Сделать **строже** можно всегда. Это сделано
специально: площадка банит за массовость, а аккаунт у вас один.

Если очень нужно поднять потолок — это правка
`ЖЁСТКИЙ_МАКСИМУМ` в `lib/monitor/guardrails.mjs`, то есть осознанное
решение, а не опечатка в конфиге. Не рекомендуется.

## Шаг 4. Проверить, ничего не отправляя

Сухой прогон: монитор поищет и покажет, что нашёл, но **никому не ответит**
(он вообще не умеет отправлять — отправка живёт в субагенте).

```bash
node lib/monitor/monitor.mjs --config config/monitor.json --dry-run
```

Что вы увидите:

```
Мониторинг: тем 2, режим dry-run

── Итоги прогона ──
Запросов к API:   3
Найдено постов:   41
Уже видели:       0
Отброшено:        33
В очередь:        8

Почему отбрасывали:
  14× старый пост (72 ч, предел 48 ч)
   9× слишком короткий пост
   6× ключевое слово в тексте не найдено (поиск дал случайное совпадение)
   4× затоптанная ветка

Бюджет ответов: 0/40 за сутки (жёсткий максимум 80)
```

**На что смотреть:**

- Если **«Найдено постов: 0»** по всем темам — скорее всего скоуп
  `threads_keyword_search` ещё не одобрен, и поиск ищет только по вашим
  постам. Это самая частая проблема на старте.
- Если много **«ключевое слово не найдено»** — ваши `ключевые` слишком узкие
  или с окончаниями. Пишите корни.
- Если всё отброшено по возрасту — поднимите `максВозрастЧасов` или ищите
  темы, где люди пишут чаще.

### Частые ошибки и что они значат

| Сообщение | Что делать |
|---|---|
| `Нет переменной окружения THREADS_ACCESS_TOKEN` | вернуться к шагу 2 |
| `Токен доступа не принят Threads … код 190` | токен истёк или отозван — выпустить новый (шаг 1.6) |
| `Превышен лимит запросов Threads` | это норма, не поломка. Подождать |
| `Опущен стоп-кран` | см. следующий раздел |
| `Threads ответил не-JSON` | запрос ушёл не на тот адрес — это ошибка в коде, показать Клоду |

## Шаг 5. Включить

Запуск мониторинга (собирает очередь кандидатов, ничего не отправляет):

```bash
node lib/monitor/monitor.mjs --config config/monitor.json
```

Ответы пишет и отправляет субагент. В Клоде:

```
запусти агента threads-monitor
```

Раз в неделю — аналитика:

```
запусти агента threads-analyst
```

### Разумный режим на старте

Первые две недели **не включайте автоматическую отправку**. Пусть субагент
готовит ответы и показывает вам, а кнопку жмёте вы. Так вы увидите, какие
ответы получаются, и успеете поправить темы и стоп-слова, пока цена ошибки
равна нулю.

## Стоп-кран: что это и что делать

Если API ответил что-то непонятное или похожее на блокировку действий,
система **останавливает всю активность целиком** и пишет причину в журнал.

Сама она не возобновится — это сделано специально: автоматика, которая сама
себя разблокирует, продолжит делать то, из-за чего её заблокировали.

**Что делать:**

1. Посмотреть причину:
   ```bash
   cat state/guardrails.json
   grep СТОП_КРАН state/actions.jsonl
   ```
2. Понять, что случилось. Чаще всего — истёк токен.
3. Исправить причину.
4. Снять стоп-кран **осознанно**, а не рефлекторно.

Проще всего показать Клоду вывод команд выше и спросить, что произошло.

⚠️ Если причина была «похоже на блокировку действий» — **не снимайте
стоп-кран в тот же день.** Подождите сутки, посмотрите в приложении, не
пришло ли предупреждение от площадки, и снизьте лимиты перед запуском.

## Что лежит в папке state/

| Файл | Что внутри | Можно ли удалять |
|---|---|---|
| `actions.jsonl` | все действия: что искали, нашли, отправили, что заблокировали и почему | нет: это ваша история и доказательство |
| `guardrails.json` | счётчики отправок и состояние стоп-крана | нет: удаление обнулит лимиты |
| `seen.json` | id уже просмотренных постов | нет: удаление приведёт к повторной обработке |
| `queue.jsonl` | очередь кандидатов на ответ | можно, если нужно начать подбор заново |
| `quota.json` | локальный учёт расхода квот API | нет |

**Всю папку `state/` нельзя коммитить в git** и нельзя чистить «чтобы
начать заново»: именно на ней держатся лимиты и защита от повторных ответов
одним и тем же людям.

Посмотреть журнал по-человечески:

```bash
# что заблокировали и почему
grep ЗАБЛОКИРОВАНО state/actions.jsonl | tail -20

# что отправили
grep ОТПРАВЛЕНО state/actions.jsonl | tail -20
```

Или просто попросите Клода: «покажи, что предохранители заблокировали за
последние дни и почему».
